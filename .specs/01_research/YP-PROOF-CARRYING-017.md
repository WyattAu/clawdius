# Yellow Paper: Proof-Carrying Edits — The Trust Ordering Must Be Mechanical and Monotone

## YP-1: Research Basis

| Source | What it establishes |
|---|---|
| Necula & Lee, *Proof-Carrying Code* (POPL 1997) | The founding discipline: the producer generates the proof (expensive, untrusted); the consumer runs a **simple, reliable, cheap proof checker** (the trusted base). |
| Yale FLINT, *Scaling PCC to Production Compilers* | PCC scales when certificates are generated by the same infrastructure that compiles the code. |
| 2026 Survey (ScienceDirect) | Informal defenses (prompt engineering, review-only) show 40–60% bypass rates — human-only evidence is the weakest tier. |
| OWASP GenAI LLM01:2025 | No fool-proof prevention — the detection tier must never be claimed as sound. |

## YP-2: The gap found in the spec

`proof_carrying_edits.lean` carried the right vocabulary but no trust
semantics: `proofMethod : String` (free text — "how the property is
verified" as prose), two vacuous rfl-theorems, and a `ProofSketch`
with a `confidence : Float` that posed as evidence. Nothing made the
trust ordering explicit, nothing prevented review-only evidence from
 masquerading as machine-checked, and nothing forced the evidence
chain to be monotone.

## YP-3: Analysis — the field's answer

Necula–Lee: the checker is mechanical and the trust ordering is
explicit. Applied to edit certificates:

- Verification methods form a **lattice**: formal > tool > test >
  review.
- A certificate is **machine-checked** iff every obligation's method is
  at least `tool` — the mechanical floor.
- The floor is **monotone**: machine evidence satisfies any weaker bar
  (downgrade safety), and **human review can never reach the machine
  floor** (review_never_machine) — no amount of review accumulates
  into formal evidence. This is why `ProofSketch` (documentation,
  confidence floats) is deliberately excluded from certification.

**Are we solving a problem the field could not?** No — Necula–Lee is
1996. The machine-checked trust ordering over *edit certificates*
(verification-method algebra for code edits, with the review-tier
boundary proven) is the estate's formal version of the discipline.

## YP-4: The corrected model

- `VerificationMethod`: formal > tool > test > review (typed — no more
  free-text methods).
- `methodAtLeast`: the trust ordering; asserted transitive (T3), with
  review weakest (T1) and formal strongest (T2).
- `machineCertified obligations`: every obligation's method ≥ tool.
- Asserted (T4): `machine_certified_downgrade_safe` — machine evidence
  satisfies any weaker acceptance bar.
- Asserted (T5): `review_never_machine` — no method below tool ever
  reaches the machine floor.
- `ProofSketch`/`confidence` remain documentation — deliberately
  outside the certification path.

## YP-5: Falsifiable predictions

- P1 (proved, T1): review-only evidence is dominated by every method.
- P2 (proved, T2): formal evidence dominates every method.
- P3 (proved, T3): the ordering composes — formal ≥ tool ≥ review
  implies formal ≥ review.
- P4 (proved, T4): machine evidence survives any acceptance-bar
  downgrade.
- P5 (proved, T5): review-only evidence can never upgrade to the
  machine floor — the certification boundary is real.
